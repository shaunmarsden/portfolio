03 / SOLUTION DESIGN / HUMAN AUTHORITY

A recommendation is not permission.

Human-Approved Service Request Workflow

Python · SQLite · fictional inputsExecuted evidence: 22-26 October 2026

THE PROJECT

A local service-request workflow where an AI-shaped recommendation cannot authorise its own execution.

Evidence & offline source →

Independent exercise.
Codex-assisted development.
No production deployment.

The problem

A useful recommendation still needs an accountable decision before it changes anything. The prototype explores that boundary using fictional service requests and a local queue assignment.

Architecture & approach

  1. Validated JSON request
  2. Rules + permitted evidence
  3. Approve / edit / reject / escalate
  4. Authorised local action + receipt

Reuse the existing retriever and Completion interface. Keep model advice disabled by default. Separate requester, reviewer and operator roles; use request IDs, decision IDs, stale-version checks and execution receipts. Make external adapters injectable so the side-effect/commit failure window can be tested with mocks.

What was actually tested

The saved walkthrough covered six requests, six decisions, two actions and 14 audit events. Another 18 mock-recovery commands challenged rollback and the external-side-effect/local-commit window. Tests cover unauthorised actions, self-approval, duplicate commands, changed content and stale versions.

A failure that changed the design

Passing tests initially missed a boundary defect: an advisor could mutate shared evidence. A correction isolated advisor inputs with a deep copy and returned structured validation errors for deeply nested JSON. The system still does not sandbox an arbitrary Python adapter.

Inspect the failure / control path +
  1. Recommendation

    Rules and permitted evidence prepare a pending request.

  2. Human boundary

    A scripted reviewer decision is checked against the current version.

  3. Execution

    A separately authorised operator executes the frozen action; a receipt makes repeats idempotent.

State-flow explanation of the tested local prototype. Scripted actors are not real independent reviewers.

The limit of the result

All review decisions were scripted fixtures. Role selection is not authentication, the audit is locally editable, and callbacks hold a SQLite write transaction. Monitoring can be lost when the store is unavailable or locked. A genuine reference passage does not authorise an access grant or queue change. Real external actions were mocked only.

Separate content support, decision authority and execution. A human approval state matters only if the action boundary enforces it; citations and model confidence cannot substitute for permission.

Contribution & validation

I set the architecture requirements, fictional-data boundary and approval requirements. Codex implemented the prototype, operated the scripted walkthroughs and tested mock failures. I did not personally operate those walkthroughs. Automated tests and agent support judgements are separate from independent human validation, which was not performed.

What the work demonstrates

API contracts, authority separation, state transitions, evidence reuse, idempotence and explicit integration failure handling.

Workplace use would require representative authorised data, accountable owners, authenticated identities, security and operational review, and evidence of actual workflow value. None is claimed here.
